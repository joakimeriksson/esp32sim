## V8 side (the cheap check)

`node --trace-wasm-compilation-times`, SECS=8 (`tier.txt`): big functions DO tier up. 1177 of 4568 generated functions reached TurboFan, including every 150-168 KB region (70-94 ms each, 23 MB peak zone memory each). Not stuck in Liftoff. But the volume is large: 12.7 s of cumulative TurboFan time (background threads) inside an 18 s run, 64 MB of wasm bodies -> 158 MB of Liftoff code. 30 s run on base: 6129 modules, 83,502,841 bytes, 635 ms synchronous `new WebAssembly.Module` on the main thread; 39.8 MB of that in the first guest second.

**Finding for the coordinator (not emitter work, not fixed here):** the matmul kernel alone is 30.5% of all generated bytes in 8 s: 128 distinct block-head PCs inside 4200f6fc..f8ba (almost every instruction is a block head: `ls dump1`), 142 block modules (5.5 MB, 55-64 KB each because three bodies x ~600 bytes per PIE instruction) and 99 region modules (15.5 MB, ~156 KB each, ~80 ms TurboFan each = ~8 s of background compile). Only 8 of those functions carry 90% of the kernel's time. Mid-block resume PCs become block heads and each grows its own region. Entering the existing block's guarded body at the index (or refusing region formation for a head that lies inside an existing hot block) would cut ~20 MB of compile work; architecturally invisible, so exact.

## Fixes

**s1 (tag hotwat-s1): PIE s8 accumulate.** Reapplied the preserved EX042 Sep 19 patch `docs/evidence/pocket-throughput-2026-09-19/s8-accx.patch` (with its 176 directed tests, fixed for today's `ready()` signature): low+high lane vectors added as i32x4, 4 `extract_lane` + 3 `i32.add` + 1 extend; ACCX read with one `i64.load`, written with one masked `i64.store`. `ee.vmulas.s8.accx.ld.ip` hot path **146 -> 115 ops**, 13 -> 12 loads, 8 -> 4 `extract_lane`. pocket-tank emits no s16 vmulas (0 sites in 5081 modules), so s16 is untouched. What differs from the parked run: same mechanism, new base (kernel share roughly doubled since the base got 38% faster) and measurement quality (the Sep 19 screens were single noisy pairs: +2.67%, -0.37%, +7.00%, +0.10%).

**s2 (tag hotwat-s2): inline exact `madd.s`/`msub.s`.** `r64 = promote(s)*promote(t) + promote(r)` (product exact in f64, one rounding), demote unless r64 is an f32 rounding midpoint (low 29 bits == 0x10000000), outside the normal f32 exponent range or non-finite; those call `h_fused` as before. 38 hot ops, no call. 3.7k new differential cases (directed double-rounding traps across exponents/signs, subnormal/overflow/NaN edges, 1500 xorshift triples); a mutant with the midpoint test disabled fails them. **Overlap: `x2/crumbs-fma` (EX170, 49e8e46c) is the same mechanism, leaner** (it mirrors libm `fma_wide_round`, halfway test only, no range test, ~10 fewer ops). Prefer EX170's emission; treat hotwat-s2 as an independent confirmation. Different from EX095 (failed "set lowest bit" recipe): no rounding recipe, hazards fall back to the exact helper.

## Not fixed, and why

- **Memory probe (~54 ops per access, the other 40% of the kernel).** With `TlbEntry::EMPTY = {lo:1, hi:0}` (emu-core/src/bus.rs:32) all three range compares are needed: every merged form lets EMPTY pass. Two compares need EMPTY = (u32::MAX, 0) and `addr >=u hi-(w-1)`; one compare needs a precomputed limit field. Both touch emu-core and the native JIT. Emitter-only savings are small: hoist the per-access TLB-null test by pointing a null TLB at a static all-EMPTY table at function entry (-3 ops, -1 branch per access), tee lo/hi into locals (-2 loads, 0 ops). EX064 (bounds reuse) screened flat at 0.39%; I did not build this.
- **PIE-mode check per PIE memory op** (5 ops): EX156 s2 preserved in exp/kernel 90d04dc6, screened 2.34% alone and flat in stack (11.92 vs 12.02). Not repeated.
- **Q/ACCX in locals** (EX156 s3, 5c9e61a9): it loaded all touched Q at entry and stored at every exit; with 64-instruction quanta that trades ~125 per-op L1 accesses for 12 boundary ones and still screened flat, which says store-forwarded L1 traffic is not the cost. Op count and compare/branch count are what is left to cut.
- `float.s` with imm 0 emits `f32.div` by 1.0 (wasm_float.rs FloatS arm; 8 per iteration). I did not check whether V8 folds it; skipping the divide when imm == 0 is a two-line change, too small for its own artifact.
- Hardware-loop emission (EX160): untouched. The pixel loop already takes the guarded static-site backedge; its per-iteration bookkeeping is LEND/LCOUNT compare + decrement + version/budget test (roughly 40 ops per 15-instruction iteration, `guarded_backedge` in wasm_emit.rs).

## Next step and exactness risk

1. Dispatcher/region formation: do not decode a new block (and region) for a PC that lies inside an existing hot block; enter that block's guarded body at the index. Removes ~20 MB of wasm and ~8 s of background TurboFan per run for this kernel. Risk: none to architecture state; block-boundary-dependent behavior (probe bloom, interrupt sampling points at block ends) must stay identical, so gate with exact.mjs.
2. Probe diet with EMPTY = (u32::MAX, 0): 54 -> ~45 ops per access everywhere. Risk: any reader that relies on `hi == 0` for empties (native JIT in xtensa-lx7/src/jit/mod.rs:219-224, esp32s3/src/bus.rs:295 `lookup`).
3. If s1 confirms: the same treatment for the saturation (branch on `(v<<24>>24) != v` instead of two selects) and fusing `zero.accx` + 4 vmulas + `rur.accx_0` inside region chunks where no entry label intervenes.
