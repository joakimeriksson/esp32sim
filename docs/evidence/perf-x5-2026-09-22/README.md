# x5 browser performance closeout — September 22, 2026

The 31 original jobs support selecting `edges-s3` and `helpers-s1s2` for a combined confirmation. Separately, they reduce median Pocket wall time by 2.15% and 1.82% and TinyDraw wall time by 5.20% and 2.99%. Those standalone gains cannot be added. Initial A/A controls report apparent gains of 0.75% and 0.70% with individual pairs spanning −0.27% to +1.65%, so small effects need caution. [All samples](results.json)

`helpers-s3` adds scope without a consistent improvement over `helpers-s1s2`: 1.59% versus 1.82% on Pocket and 3.57% versus 2.99% on TinyDraw, each compared independently with the base. Every tails variant regresses both workloads. `edges-s4a` trades a Pocket regression for a TinyDraw improvement and `edges-s4b` regresses Pocket. Host build/dispatch screens and `pie-s1` supply no persuasive execution-speed gain. These are selection judgments from the measured samples, not claims of statistical significance. [Receipts](results.json)

The size proposal removes default DWARF from production WASM, reducing the integrated artifact from 12,219,972 to 2,088,105 bytes (82.91%) while retaining its `name` section and explicit debug overrides. Recompilation changes address and symbol-order immediates, so executable byte identity between debug configurations is not claimed. No download/startup latency was measured. The final source build is byte-identical to the frozen artifact queued for browser confirmation. [Size validation](size-validation.json), [final source equivalence](published-equivalence.json)

The initial screen contains 218 timed browser arms. Each job JSON retains every arm in execution order, pair reductions, ratio-of-median reduction, exact work totals, console hashes, frames, JIT counters and aggregate load. Positive reduction means less wall time; negative means slower. The summary is `100 × (1 − median(candidate wall) / median(baseline wall))`, which can differ from the median of the pair percentages. [Result index](results.json), [harness implementation](../../../tools/browser-benchmark/run-pairs.py)

To repeat the browser workload, create a virtual environment with `uv venv .venv` if absent, supply asset manifests matching the recorded input hashes and run:

```sh
uv run --offline --no-project --python .venv/bin/python python tools/browser-benchmark/run-pairs.py "$OUTPUT" \
  --baseline-tree "$BASE_TREE" --candidate-tree "$CANDIDATE_TREE" \
  --baseline-wasm "$BASE_WASM" --candidate-wasm "$CANDIDATE_WASM" \
  --assets "$ASSETS_JSON" --pairs 4
```

The runner serializes timed jobs, waits for competing benchmark/build processes and interactive browsers, and runs exact gates before timing. Gate batches can use four processes before the timed phase. Aggregate load is retained per arm; load averages cannot establish an otherwise idle machine or quantify thermal behavior. This is a small, nonrandomized screen on one machine and two workloads, with a positive A/A bias and no confidence intervals. Repeated candidates share a baseline but their jobs ran at different times. [Arm load and order](runs/edges-s3.json), [original runner hash](source-manifest.json)
